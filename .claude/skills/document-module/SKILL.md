# 레거시 모듈 문서화

## 원칙

- 분석 대상 폴더의 파일은 읽기만 한다. 수정 · 생성 · 삭제하지 않는다.
- 산출물은 `docs/<모듈명>/ARCHITECTURE.md`, `ERD.md`, `BUSINESS-RULES.md` 세 개다.
- `<모듈명>` 은 폴더 이름이 아니라 아래 셋 중 하나다. 다른 경로면 멈추고 묻는다.
  - `legacy/item-bank-php` → `item-bank` · `legacy/assignment-thymeleaf` → `assignment` · `legacy/grade-mssql` → `grade`
- 인자 `$ARGUMENTS` 의 첫 값은 모듈 경로, 나머지는 범위 제한이다. 범위 제한이 있으면 그 범위만 보고, 각 문서 머리에 "분석 범위"로 적는다.
- 근거 경로는 모듈 폴더 기준으로 적고, 스키마 등 모듈 밖 파일은 문서 머리에 별칭(예: `schema`)을 정해 쓴다.

## 절차 (순서 고정, 단계마다 파일 저장 후 다음 단계로)

1. **계획 제시** — 읽을 파일 목록, 단계별 산출물, 범위 제한을 먼저 보여 준다. 파일은 아직 쓰지 않는다.
2. **진입점** — URL · 화면 · 저장 프로시저 등 외부에서 들어오는 지점을 찾아 `ARCHITECTURE.md` 에 저장한다.
3. **의존 관계** — 진입점에서 호출하는 공통 코드 · 외부 라이브러리 · DB 연결을 추가해 `ARCHITECTURE.md` 를 갱신 · 저장한다.
4. **데이터 흐름** — 읽고 쓰는 테이블 · 뷰, 관계, 읽기 · 쓰기 위치를 `ERD.md` 에 저장한다. 뷰 · 프로시저 정의가 `db/` 에 있으면 그것도 읽는다.
5. **비즈니스 규칙 후보** — 조건문 · SQL 에서 규칙을 뽑아 `BUSINESS-RULES.md` 에 저장한다. 끝에 매직 넘버 표, "주석만 있고 코드로 확인되지 않은 것" 표, "같은 규칙이 여러 곳에 다르게 구현된 곳" 표를 붙인다.
6. **표본 점검 추천** — 아래 "마지막 단계"를 채팅으로 출력한다.

각 단계가 끝나면 저장한 파일 경로와 한 줄 요약을 보고한다. 앞 단계 파일을 저장하지 않고 다음 단계로 넘어가지 않는다.

## 규칙 형식 (`BUSINESS-RULES.md`)

```markdown
### BR-01 규칙 제목

- 규칙: 한 문장. 조건과 결과를 함께 쓴다.
- 근거: `search.php:44`, `search.php:98-99`
- 근거 코드:
  ```php
  근거 줄을 그대로 옮긴 1~3줄
  ```
- 확신도: 확실 | 추정 | 미확인
- 비고: 주석과 코드 불일치, 매직 넘버, 다른 곳과의 차이 등
```

- ID 는 `BR-01` 부터 연번이다. 절은 기능 단위(검색 · 정렬 · 제외 조건 · 등록 검증 등)로 나눈다.
- 주석과 코드가 다르면 코드 기준으로 규칙을 쓰고, 주석은 비고에 남기고 제목에 ⚠ 를 붙인다.
- DB 동작(collation, 동시성 등)에 기대는 판단은 "추정"으로 두고 무엇을 확인해야 하는지 적는다.

## 하지 말 것

- 존재하지 않는 함수 · 파일 · 테이블 · 컬럼을 적지 않는다. 이름을 쓰기 전에 Grep 으로 정의가 실제로 있는지 확인한다.
- 호출 방향을 뒤집어 적지 않는다. "A 가 B 를 호출한다"는 A 파일 안의 호출 줄번호를 근거로 댈 때만 쓴다.
- 코드에 없는 규칙을 만들지 않는다. 주석 · 화면 문구 · 변수 이름 · 도메인 상식만으로 규칙을 올리지 않고, "주석만 있음" 표로 보낸다.
- 근거 줄번호는 Read 로 본 현재 파일 기준이다. 인용한 코드가 그 줄에 실제로 있는지 다시 확인한다.
- 없는 기능(예: 수정 화면이 없으면 "수정 시 검증")은 규칙을 지어내지 말고 "이 모듈에 없음"이라고 적는다.
- `modern/` 코드나 기존 문서를 근거로 삼지 않는다. 기준은 레거시 코드와 `db/` 스키마다.

## 마지막 단계: 사람이 표본 점검할 규칙 3개 추천

`BUSINESS-RULES.md` 에서 3개를 골라 채팅으로 제시한다. 파일에는 쓰지 않는다.

- 반드시 **가장 그럴듯한 규칙** 1개를 넣는다 — 도메인 상식에 잘 맞아 사람이 코드를 안 보고 넘어가기 쉬운 규칙.
- 나머지 2개는 주석 · 코드 불일치(⚠), "추정" 확신도, 같은 규칙이 여러 곳에 다르게 구현된 것 중에서 고른다.
- 형식: `| ID | 고른 이유 | 확인할 파일:줄번호 | 확인 방법(코드 읽기 · 실행 · DB 조회) |`
- 점검 결과를 받으면 `BUSINESS-RULES.md` 끝에 "검증 이력" 절(날짜 · 점검자 · ID · 결과 · 틀린 유형)을 추가한다.
